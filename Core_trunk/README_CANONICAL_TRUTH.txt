WHY THIS FILE EXISTS
────────────────────
The combinatorial pipeline used to be order-sensitive in a subtle place:
FW_Group's `SubsetsG` enumerator iterates source rows by INDEX, and
concatenated row contents in index order.  The "source list order" was
inherited from whatever order distinctify happened to return rows in,
which depended on:

  - which intermediate store backend was active (PG vs in-JVM)
  - which SQL plan PostgreSQL picked for SELECT DISTINCT
                                            (HashAggregate vs Sort+Unique)
  - PostgreSQL version, work_mem, statistics, page layout
  - parallel combinatorial library emission timing

Two equally-valid orderings of the same 4-row source produced 13 vs 14
distinct subset-concatenations for sheet E.  That single-row delta fanned
out through fw_opt4's C(30,4) cartesian to a 694,114-row gap between
"PG-distinct mode" and "Java-distinct mode" outputs on the
test14042026.xlsx fixture.  Neither was wrong; both were faithful
measurements of an algorithm whose ordering rule was never specified.

Iter4 Step 8 (TableDataDistinctor MIN(combi_id) GROUP BY ORDER BY) and
Step 10 (SheetWorker FW_Group content-sort of inListFWasList) together
close the spec hole:

  - Step 8 makes PG and in-JVM stores assign the same combi_id ordering.
  - Step 10 makes FW_Group's source list a PURE FUNCTION OF THE DATA,
    independent of any cid ordering, store backend, or library version.

Together they give the engine a single deterministic output that does
not drift across PG versions, JVM versions, or library updates.


CANONICAL TRUTH — test14042026.xlsx
───────────────────────────────────
Under the post-Step-10 codebase, against the reference fixture, with
default distinctify settings, the engine MUST produce:

   fw_final = 4,644,864 rows
   fw_opt4  = 33,674,483 rows

These numbers are invariant across:

   core.intermediate.storage ∈ { pg, memory }
   core.precompute           ∈ { auto, db, java }
   PostgreSQL version, plan choice, work_mem, ANALYZE state
   Combinatorial library version (dpaukov / ghYura)
   Parallelism setting (core.threading.parallelizeSubCombosIfPossible)
   JDK version
   Hash function changes in JVM or PostgreSQL

If a run on test14042026.xlsx produces ANY OTHER fw_opt4 row count,
either (a) the input file was modified, (b) the distinctify flags
were changed (sampleAndSkip / distinctifyJavaSide), or (c) a
regression was introduced.  Investigate immediately.


HISTORICAL NOTE — Why "34,368,597" appears in older logs
────────────────────────────────────────────────────────
The legacy pre-Iter2 codebase (Opus 4.6 baseline) reported
fw_opt4 = 34,368,597 on this fixture.  That number was a faithful
measurement of THAT code's behavior on PG with HashAggregate ordering.
It was reproducible on a given PG version but would silently shift if
the planner picked a different distinct strategy.  The legacy code did
not write canonical-truth invariants — it just emitted whatever its
implementation produced.

Opus 4.6's measurement was NOT wrong.  The new number (33,674,483) does
not invalidate it.  They are two correct measurements of the same
algorithm under two different (unspecified) orderings.  Read on.


WHY THE "BIGGER" NUMBER ISN'T "MORE DATA"
─────────────────────────────────────────
Common confusion: "34,368,597 > 33,674,483 — did we LOSE 694,114 rows?"
Answer: NO.  Same physical generator emissions, just a different
accidental-collision pattern during encoding.  Walked example follows.

Take sheet E.  After directive[0] FW_Subsets, fw_53 holds these 4 rows:

   row_a = []
   row_b = [489]
   row_c = [490]
   row_d = [489, 490]

The next directive runs FW_Subsets over fw_53 IN FW_Group MODE.  This
enumerates the 16 subsets of the 4-row list and, for each subset,
concatenates its rows with the FW_Separator value (515).  Each subset
is identified by INDICES into the list — so subset {1, 3} means
"first and third rows in iteration order".  Critically: the
concatenation order is the index order, not any canonical row order.

PG-HashAggregate happens to feed FW_Subsets a permutation like:

   list_PG = [ [], [489], [490], [489,490] ]
                row_a row_b  row_c  row_d
   subset {1,3} → row_b ⊕ 515 ⊕ row_d
                = [489] ⊕ 515 ⊕ [489,490]
                = [489, 515, 489, 515, 490]

In-JVM LinkedHashMap distinctify feeds it a DIFFERENT permutation
(post-Iter2 insertion order):

   list_JVM = [ [], [489,490], [489], [490] ]
                row_a  row_d   row_b  row_c
   subset {1,3} → row_d ⊕ 515 ⊕ row_c
                = [489,490] ⊕ 515 ⊕ [490]
                = [489, 515, 490, 515, 490]

Same subset of rows, different concatenated byte string.  This is the
spec hole.

Out of the 15 non-empty subsets per source list:

   PG-HashAggregate ordering → 1 pair of subsets accidentally
                                produces the same byte string
                                → 14 distinct rows in fw2_53
   JVM-insertion ordering    → 2 pairs accidentally produce the
                                same byte string
                                → 13 distinct rows in fw2_53

Sheet E loses ONE distinct row in JVM mode vs PG mode, purely due to
encoding-collision count.  No row vanishes upstream.

This one-row delta fans out through fw_opt4's C(30,4) cartesian.
Sheet E participates in C(29,3) = 3,654 of the 27,405 four-way
combos.  Each such combo cartesian-multiplies sheet E's distinct
count by the cartesian over the other 3 optional sheets (mean ~190
rows per combo on this fixture):

   1 (sheet E delta) × 3,654 combos × ~190 mean cartesian
       ≈ 694,260 rows  ≈  34,368,597 − 33,674,483
                       =  694,114  ✓

A third hypothetical ordering — say, lex-sort source rows by content,
or sort by content-length-then-lex — could yield yet another count
(say 12, 14, or even 15 distinct concatenations) on sheet E, and a
correspondingly different fw_opt4.  All such counts are mathematically
valid outputs of an algorithm whose ordering rule was simply never
specified.

Iter4 Step 10 picks "lex-sort by content" as the canonical ordering
because it depends only on the data (not on cid, not on PG plan
choice, not on JVM hash function, not on combinatorial library
version, not on parallelism setting).  That choice locks in
33,674,483 as the future-proof reproducible answer.


HOW TO RESTORE IF DELETED
─────────────────────────
A backup copy lives at:

   src/main/resources/README_CANONICAL_TRUTH.txt

If the project-root copy is missing or unreadable, Bootstrap falls back
to the classpath copy and emits a WARN log line so the operator sees
the project root has drifted from its expected state.  Manual restore:

   cp src/main/resources/README_CANONICAL_TRUTH.txt ./README_CANONICAL_TRUTH.txt

  having made such a change, DO NOT update this file — find the
