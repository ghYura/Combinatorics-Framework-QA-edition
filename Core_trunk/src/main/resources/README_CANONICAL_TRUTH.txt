HOW THE TOTALS ARE BUILT — and how to localize a change
────────────────────────────────────────────────────────
fw_final is the Cartesian product of the mandatory sheets' final tables.
|fw_opt_k| is e_k(n_1, ..., n_m): the k-th elementary symmetric polynomial of
the final row counts of the optional sheets that contribute.  The fixture
declares 32 FW_Optional sheets; E1E2_3 and E1E2_6 end empty and are not
registered, so 30 contribute.  Both builds above satisfy e_1..e_4 exactly.

A changed total therefore reduces to changed per-sheet counts: compare the
Core log's "[DIAG] Sheet <S> ... rows AFTER distinctify" lines between runs.

WHAT CHANGED BETWEEN THE TWO BUILDS — three optional sheets
───────────────────────────────────────────────────────────
   Sheet     e38766b .. ca8c646     current     Why
   G, M, N   16 rows each           8 each      grouped FW_Cartes(X)
   E         13                     13          unchanged
   (all other 26 contributing sheets are identical)

G, M and N run FW_Cartes -> FW_Group -> FW_Cartes(X).  The author's rule, and
his original code (Main.java, 2020), is "grouped rows x X" (X x rows for
FW_Cartes_first).  The refactored code up to ca8c646 paired the grouped rows
with themselves and ignored X; that behaviour duplicated
FW_Group -> FW_PermutR(2), which still produces those 16 rows.

SHEET E IS A CONVENTION, NOT A LAW
──────────────────────────────────
Sheet E runs FW_Subsets -> FW_Group(rewrites) -> FW_Separator(S1) ->
FW_Subsets over the four source rows of FW_Subsets({e1, e2}):
[], [e1], [e2], [e1, e2].

The grouped pass concatenates the rows of each subset IN LIST ORDER.  The
rewrite lines turn [] into a real code (FW_EMPTY_STRING) and flatten the rows,
and the separator weaves its code between all codes, so row boundaries are
erased and different subsets can render identically — e.g. {[e1, e2]} and
{[e1], [e2]} when [e1] precedes [e2], and {[], [e1, e2]} and
{[], [e1], [e2]}.  How many such collisions occur depends only on the order
of the four source rows:

   over all 24 orders:   13 distinct rows (6 orders), 14 (6), 15 (12)

(computed by independent emulators that reproduce Core's actual rows, and
re-checked on 2026-09-28 against the fixture's own FW_Seq rewrite lines).

   Content order (Iter4 Step 10, lexicographic by codes):  13   <- current
   Generation order [], [e1], [e2], [e1, e2]:              13
   PostgreSQL 18.6 HashAggregate order of the legacy
   DISTINCT query ([e1, e2], [], [e1], [e2]):              14

The original code took the rows in whatever order PostgreSQL's DISTINCT
returned (no ORDER BY), so its count could vary with the plan and version.
Step 10's content sort makes E a pure function of the data: the count no
longer depends on the store backend, PostgreSQL plan or version, JVM hashing,
library version or parallelism.  It does NOT make 13 "the" answer: another
ordering rule would give another, equally valid count.  13 is the declared
convention; changing it is the author's decision.

ERRATUM to the earlier walk-through in this file: it attributed
[], [e1], [e2], [e1, e2] to PostgreSQL and counted 14 for it.  That order
is the generation order and gives 13: it misses the second collision, which
involves the empty row once [] has become a real code.

HOW TO REPRODUCE
────────────────
1. Build Core:  mvn -q -f pom.xml -pl Core_trunk -am -DskipTests
                -Dexec.skip=true package
2. Run Core alone on a copy of the fixture into a FRESH database, with the
   optional-table contract restricted to sizes 1..4 (a complete 1..32
   contract is infeasible): e.g. bundle.stages.stage_core() with an
   OptionalTableContract whose produced/consumed sizes are (1, 2, 3, 4).
3. SELECT count(*) FROM fw_final, fw_opt1 .. fw_opt4, and check each fw_opt_k
   against e_k of the per-sheet counts in core.log.

Resources: the database reaches ~5.5 GB (8.3 GB on the old build), dominated
by fw_opt4 — use fast storage (the 2026-09-28 runs used a PostgreSQL cluster
on tmpfs).  With core.precompute=java the fw_opt4 distinct pass alone holds a
~1 GB seen-hash (~1.6 GB on the old build); at -Xmx4g the HeapWatchdog reached
95% and signalled an abort, at -Xmx8g both builds completed (4 min 43 s and
7 min 40 s of Core time).

   cp src/main/resources/README_CANONICAL_TRUTH.txt ./README_CANONICAL_TRUTH.txt
