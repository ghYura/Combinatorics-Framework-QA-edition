  Короткий ответ

  generator_trunk/constraints/ — это отдельный, неинвазивный слой «связей/бондов» (bonds layer), который умеет запрещать комбинации значений, чего сам Core делать не умеет. Он состоит из:

  - движка — sieve.py (460 строк, несущая конструкция);
  - двух «компиляторов модели» поверх движка — bondmatrix.py (матрица) и graphspec.py (граф-нити);
  - тонкого формульного тира — predicate.py;
  - четырёх графических редакторов, которые все компилируют в один и тот же sidecar.json: bondmatrix.html, graph_editor.html, react_flow/ (React Flow), blockly_when/ (Blockly).

  И всё это сходится в один артефакт — sidecar {version, params, constraints}, который bundle_run --sieve применяет между Core и Reader.

  ---
  1. Зачем слой вообще существует (архитектурный корень)

  Это записано прямо в шапке sieve.py:3-16 и в docs/07_CONSTRAINTS_GUIDE.md:1-7:

  ▎ Core DSL — это генератор, а не язык ограничений. У него нет глагола «запретить комбинацию значений». FW_Exclude — это sheet-level (откладывает целый лист в exclude-map под brace-join), а скобка FW_(...) — это JOIN двух
  ▎ result-таблиц, а не фильтр. Оба — порождающие (добавляют строки), а не вычитающие.

  Поэтому «разрешённые/запрещённые бонды между значениями» (химическая аналогия: атомы несут параметры; бонд разрешён/запрещён формулой над параметрами, и важна близость/порядок) вынесены в отдельный слой, который НЕ трогает Core — он
  фильтрует таблицу, которую Core уже произвёл.

  2. Трёхуровневая архитектура (author → enforce → fallback)

  Из sieve.py:10-16:

  ┌──────────┬────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┬───────────────────────────────────────┐
  │ Уровень  │                                                                     Что делает                                                                     │               Где живёт               │
  ├──────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┼───────────────────────────────────────┤
  │ author   │ декларативный sidecar (params + constraints)                                                                                                       │ bondmatrix/graphspec/predicate + 4 UI │
  ├──────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┼───────────────────────────────────────┤
  │ enforce  │ SIEVE — вставлен между Core и Reader, удаляет строки-нарушители из fw_final до дорогого Reader/Executor                                            │ sieve.py (sieve_fw_final)             │
  ├──────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┼───────────────────────────────────────┤
  │ fallback │ оракул Executor (FW_VAR в TAIL) для ограничений, которым нужен собранный и исполненный кандидат (сложная дистанция/порядок, stateful, алгоритмика) │ TAIL-слот спеки                       │
  └──────────┴────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┴───────────────────────────────────────┘

  Ключевая мысль: статика → sieve, поведение во время выполнения → оракул. Sieve работает только над конечными метаданными значений (params), он не исполняет кандидатов (docs/07:79-81).

  ---
  3. Модель данных

  Sidecar ({version:1, params, constraints}):

  - params: {sheet: {value: {attr: ...}}} — числовые/любые атрибуты на каждое значение (для формульного тира).
  - constraints[]: каждый — бинарный бонд между двумя листами:

  { id, polarity:"forbid"|"require", sheets:[sx,sy],
    (pairs:[{sx:vx, sy:vy}, ...]   ИЛИ   when:"<формула>"),
    gate:{} | {adjacent:true} | {within:N},
    desc }

  Две формы бонда — это и есть «оба уровня, которые ты хотел»:
  - enumerated pairs — простое «a11 никогда с c11», параметры не нужны;
  - when-предикат — компактное «forbid when A.charge*C.charge>0», нужны params.

  «Строка» (row) для движка — это упорядоченный список размещений: [{sheet, value, pos}, ...], где pos = индекс в собранной выходной последовательности (порядок слотов; для упорядоченного FW_Permut-листа — его порядок) (sieve.py:85-87).

  Gate (позиционный, «химия близости/порядка», sieve.py:68-75):
  - {} — любое со-вхождение;
  - {adjacent:true} — |pos_x − pos_y| == 1;
  - {within:N} — |pos_x − pos_y| ≤ N.

  Polarity (sieve.py:161-163): forbid — срабатывание бонда убивает строку; require — отсутствие бонда (на gated-паре) убивает строку.

  ---
  4. Ядро — sieve.py

  row_violations(row, sidecar) (:132-170) — сердце. Для каждого constraint (ровно 2 листа, иначе пропуск): берёт все размещения px листа sx и py листа sy, пропускает одинаковый pos, проверяет gate, затем
  - если when → _eval_pred(expr, ns), где ns = {sx: <SimpleNamespace атрибутов+value+pos>, sy: ...};
  - иначе → _pair_match(pairs, ...).

  (forbid and holds) or (require and not holds) → строка нарушена.

  Безопасность предиката (:43-48): ограниченный eval без builtins, белый список функций (abs/min/max/round/len/int/float/bool), regex-бан __/import/lambda/:=/exec/eval/open/globals/locals. Это тот же приём, что в difftest-eval
  репозитория.

  Отчёт о влиянии — sieve() (:188-227, «STEP 35»): чистый dry-run, ничего не удаляет. Считает scanned, matched[rule_id], overlap (строки, убитые ≥2 правилами), unique_removals, retained + ограниченные примеры отвергнутых/удержанных
  строк.

  Боевой путь — sieve_fw_final(conn, ...) (:290-361) — та же логика над таблицей fw_final живого Core. Тут самая тонкая и важная вещь — кодировка fw_final (проверена вживую на diff_fuzz_run):

  ▎ Строки несут per-sheet колонки combos<key>_<sheet> smallint[]. Это дельта-против-baseline:
  ▎ - пустая/NULL ячейка ⇒ baseline-значение слота (первое значение слота);
  ▎ - непустая ⇒ код отклонившегося значения (декод через таблицу NumberToValue1).
  ▎
  ▎ (HEAD с одним значением всегда baseline ⇒ всегда пуст; слот из 3 значений отклоняется в 2/3 строк ⇒ 162/243 непустых.) Поэтому обязательно передавать baseline {sheet→value}, иначе baseline-комбинации молча теряются.

  build_maps_from_db() (:365-404) выводит (code2val, baseline, combos_col, sheet_order) из живой БД: коды из NumberToValue1 (whitespace-stripped, чтобы совпасть с авторскими значениями), baseline — из строки-базы
  fw_final_base/_base_copy (источник истины, не догадка по спеке). dry_run=True только считает; False — DELETE ... WHERE combi_id = ANY(...).

  ---
  5. Где это стоит в цепочке Bundle

  Твоя цепочка generator-(Core+DB)-Reader-(Executor+DBresults)-(Analyzer+ownDB) — и точное место sieve в ней:

  fwgen gen                 spec(TOML/JSON/YAML) → Core-воркбуки (XLSX) + emit_sidecar→sidecar.json
     │                      (fwgen.py:912 emit_sidecar; params/constraints парсятся в parse_spec, :860-879)
     ▼
  [2/5] CORE (Java)+mainDB  заполняет fw_final (combos*-дельта), NumberToValue1, fw_final_base
     ▼
  [2.5/5] SIEVE  ◄── ВОТ ОН: stage_sieve (bundle/stages.py:274-305)
     │             sieve_fw_final(dry_run=False) — DELETE нарушителей IN PLACE. Core не тронут.
     ▼
  [3/5] READER (Java)       пересобирает выжившие комбинации → исходники кандидатов + Results DB
     ▼
  [4/5] EXECUTOR (py/Java)  исполняет; TAIL ставит FW_VAR — это и есть fallback-оракул
     ▼
  [5/5] ANALYZER + свой DB  собирает строки `app=...` по целям

  CLI-поверхность (bundle/cli.py):
  - python3 bundle_run.py <spec> --sieve — включает деструктивную стадию (:656-662); есть resume-логика, считающая sieve идемпотентным (:906-937).
  - python3 bundle_run.py constraints explain <spec> [--db <core-db>] — список правил + (с --db) сколько каждое удалит, overlap, примеры. Недеструктивно (cmd_constraints, :1511-1551).
  - constraints dry-run <spec> --db ... — те же цифры, проверяет что fw_final не изменился (96→96), тогда как реальный sieve даёт 96→72.

  Параметры и ограничения можно класть прямо в спеку как [[params]] и [[constraints]] — см. живые примеры:
  - diff_fuzz_when/diff_fuzz_when.toml:131-163 — when-форма (O1.n + O3.n > 4);
  - diff_fuzz_sieve/diff_fuzz_run.toml (хвост) — pairs-форма (ban_O1eq1_with_O3eq3).

  6. Графический слой — ровно то, что ты задумывал

  Твоя формулировка: «слой поверх input data → XLSX/TOML/JSON → (generator-Core-…), где можно рисовать линии-связи между элементами и редактировать эти логические линии какой-то логикой». Он реализован, причём в четырёх вариантах, и все
  компилируют в один sidecar.json. Лестница сложности:

  (1) Bond-matrix — bondmatrix.py / bondmatrix.html
  Строки = значения листа A, столбцы = листа B; клик по ячейке = запретить пару (бонд). Самый дешёвый и интуитивный, уровень enumerated-pairs (общий случай). Self-contained HTML без зависимостей, живой расчёт «removes N of M».

  (2) Граф-нити — graphspec.py / graph_editor.html ← это и есть «рисовать линии между элементами»
  Узлы = ячейки-значения, сгруппированные по листам в колонки; «нить» (ребро) между двумя узлами = запрещённый бонд. Cross-sheet — first-class. Двухслойный дизайн: HTML node-div'ы + прозрачный SVG-оверлей с линиями. Кликнул узел в одном
  листе, кликнул в другом — провёл красную нить; клик по нити — удалил.

  Здесь зафиксирован главный архитектурный принцип (graphspec.py:6-8): ребро ссылается на два ID-сущности [sheet, value], НИКОГДА на пиксели. То есть линии — логические (entity↔entity), а не нарисованные координаты. Группировка: рёбра
  по неупорядоченной паре листов (+gate+polarity) → один constraint на группу (to_sidecar, :47-63).

  (3) React Flow — react_flow/GraphEditor.jsx (+ graphspec.js)
  Та же модель, но «полированная»: настоящий node-edge редактор @xyflow/react, onConnect тянет ребро (только cross-sheet, :60-68), graphToSidecar (зеркало Python-версии) даёт тот же sidecar.

  (4) Blockly when — blockly_when/ ← это «редактировать логические линии какой-то логикой»
  Визуальный блочный редактор формул: блок forbid SHEETA × SHEETB, gate G, when <boolean expr> + блок fw_param (A.charge) + стоковые math/logic блоки Blockly. Перетащил формулу A.charge × C.charge > 0 → Python-генератор Blockly выдаёт
  строку → toSidecar собирает when-предикат. predicate.py — это headless-доказательство, что сгенерённая строка корректно проходит через тот же sieve (живьём проверено O1.n+O3.n>4 → 81/81), так что UI достаточно выдать правильную
  строку.

  Связь с XLSX/TOML/JSON

  Листы и значения редакторы берут из реальной спеки, не выдумывают:
  graphspec.py --spec <spec> --sheets-json public/sheets.json
  spec_sheets() (graphspec.py:201-214) читает спеку через fwgen.load_spec и отдаёт {sheet:[values]}; emit_sheets_json() пишет sheets.json, который React/Blockly-приложения фетчат в рантайме (GraphEditor.jsx:50-58,
  blockly_when/main.js:6-11). А сама спека может приходить из XLSX → JSON — это родословная v25 «Pro Data Engine» (PyQt6 GUI), вшитая в fwgen.py:5-9; в fwgen_gui.py есть кнопка «Batch XLSX→JSON». То есть полный замысел:

  input data → XLSX/TOML/JSON → fwgen spec → sheets.json
     → [граф/матрица/Blockly: рисуешь линии] → sidecar.json
     → bundle_run --sieve → (Core → SIEVE → Reader → Executor → Analyzer)

  8. Границы (честно)

  - Sieve v1 — только бинарные бонды (ровно 2 листа). Тернарные+ молча пропускаются (с warning) или валят --strict. Это записанное ограничение, не баг.
  - Предикаты только над конечными params — никакого рантайм-поведения (это оракул TAIL).
  - Селективность неизвестна заранее → bundle plan отдаёт post-sieve как bounded [0, mandatory], не точку (fwgen.py:493-507, cli.py:1370-1377).
  - Риск над-фильтрации: неверный constraint может убрать ровно те случаи, что вскрыли бы дефект → покрытие правил надо валидировать known-pass/known-fail контролями (docs/07:82-83).
  - Док-дырка: и sieve.py, и fwgen.emit_sidecar ссылаются на constraints/sidecar_schema.md, но файла нет — стоит дописать (схема сейчас живёт только в докстрингах).

  9. Состояние графического слоя и куда расти

  Что есть сейчас: 4 рабочих редактора, все → один sidecar; нити на entity-ID (не пиксели); живой расчёт impact в HTML; загрузка листов из реальной спеки. Что в редакторах пока не выведено в UI (а в модели/движке уже поддержано):

  - gate (adjacent/within N) — есть в Blockly-блоке, но в matrix/graph UI зашит {};
  - polarity require — движок умеет, UI везде хардкодит forbid;
  - params-редактор — when-тир требует params, но HTML-граф эмитит params:{} (формулы приходится дописывать руками/через Blockly);
  - двусторонний round-trip из существующего sidecar в UI — есть from_sidecar в Python, но HTML/React грузят только листы, не уже-нарисованные нити;
  - тернарная арность — упирается в «sieve v1 = бинарные».

  Это естественная дорожная карта, если решишь поднимать графический слой из состояния «4 демо» в единый продукт.
