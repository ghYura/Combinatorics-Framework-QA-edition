## Real framework business flow

```text
TOML spec / workbook-first UI
        |
        v
plan + budget/preflight + optional Face 2 draw
        |
        v
Generator -> XLSX/JSON schedule
        |
        v
Core -> PostgreSQL fw_final + fw_opt* relations
        |
        +-> optional exact drawing / seed-derived bias
        v
mandatory sieve -> deletes invalid fw_final rows
        |
        v
Reader -> reconstructs candidates, applies deferred optional bonds,
          reconciles counts, writes legacy handshake + Handoff v2
        |
        v
Executor -> executes/classifies/repeats -> legacy results + results_v2
        |
        v
Analyzer -> repeat aggregation, declared/exploratory objectives,
            Pareto/front algorithms, provenance, optional BundleSeed
        |
        +-> optional iterate loop
```

The normal Bundle launcher owns this order. Core's standalone `reader.autoLaunch` path is a
fire-and-forget compatibility path and is not the Bundle lifecycle. For the live candidate gRPC
transport, the launcher starts the Java Executor receiver during the Reader stage, Reader streams
to it, and the later Executor stage adopts and drains that process.

## Component truth

### Generator and control plane

- `fwgen_cli.py` exposes `list`, `gen`, `validate`, `json`, `coverage`, `handshake`, `preview`,
  `new`, `scaffold`, and `graph`.
- Generation supports full compact schedules, materialized schedules, k=1 baseline-plus-one-axis
  ablation, n-wise reduction, and budget-aware automatic selection.
- The Bundle CLI plans, runs, resumes, cancels, cleans, diagnoses, benchmarks, inventories,
  iterates, and serves optional HTTP/gRPC gateway surfaces.
- Configuration precedence is in-source defaults, optional ignored development defaults,
  configuration file, environment, then CLI. Later layers win. Resolved artifacts are redacted.
- Some utility/generator scripts have import-time write or execution effects. In particular, the
  companion SUT's `FW_scenario_inputs/gen_scenarios.py` overwrites workbooks and a README when
  imported. Treat such modules as commands, not import-safe libraries.

### Core

- Accepted schedule formats are XLSX, JSON, TOML, and YAML, selected explicitly or by extension.
- Core can provision or destructively recreate its target database according to configuration.
- It maps values to 16-bit codes, evaluates first- and second-order combinatorial directives, and
  materializes mandatory and optional relational products.
- Intermediate storage can be PostgreSQL, in-memory Java, or switchable Java-to-PostgreSQL under
  heap pressure. Direct `Core_trunk/fw.properties` and Bundle-rendered profiles intentionally use
  different defaults; do not conflate them.
- After final assembly, Core deliberately removes intermediate `fw_*` tables and the final-base
  staging table. Operators must not expect those tables to remain for post-run debugging.
- The canonical multi-million counts in `Core_trunk/README_CANONICAL_TRUTH.txt` are a source
  contract. They were not regenerated during this audit.

### Reader and Handoff v2

- Candidate transports are `loose-files`, `sharded`, and `grpc`.
- Setting a gRPC host/port alone does not select gRPC; `reader.candidateSink` / the launcher
  `--candidate-sink` value is authoritative.
- Current launcher gRPC is Java-only, verdict-mode, Handoff-v2, and `trusted-local`. It is a
  plaintext, unauthenticated trusted-host transport; use loopback or an equivalently protected
  network boundary. It leaves no reusable on-disk candidate corpus.
- Reader count reconciliation is normally fail-closed. A documented final-plus-optional control
  count case remains warning-level while actual sink and manifest counts are still reconciled.
- Database passwords are intentionally absent from Handoff v2.

### Executor and results

- Both Java `MainWatch` and Python `py_executor.py` consume Handoff v2; legacy handshakes remain an
  explicit compatibility path.
- Canonical outcomes are `PASS`, `DOMAIN_FAIL`, `BROKEN`, `TIMEOUT`, `INFRA_FAIL`, `SKIPPED`, and
  `CANCELLED`.
- The current immutable result-sample identity is
  `(run_id, candidate_id, attempt, repeat_idx, env_id)`. The retired three-column index is dropped;
  there is no current selected-final partial index. Retry attempt and intentional repeat are
  different axes.
- Repeat scope `metrics` keeps one canonical verdict while retaining metric samples. Repeat scope
  `all` records each full verdict repeat. Runtime launcher support is policy- and language-bounded;
  executor pools greater than one are not interchangeable with repeat distribution.
- Legacy rows and `results_v2` rows use one combined transaction in the Python path. Schema
  capability checks are strict in Bundle preflight; some standalone legacy Java initialization
  paths retain compatibility-oriented nonfatal behavior.

### Analyzer and feedback

- Inputs include K/V, JSON, CSV-like/multi-line forms, streaming data, and database-backed flows.
- Formal mode uses only declared objectives and enforces corpus/provenance requirements;
  exploratory mode can discover additional axes.
- Implemented multiobjective families include NSGA-II (default), NSGA-III, SPEA2, and MOEA/D.
- Repeat aggregation includes per-candidate medians and order-statistic confidence intervals.
- `BundleSeed` and the CLI iterate loop provide bounded feedback into later runs.
- The canonical offline regression command is `bash Analyzer_trunk/run-tests.sh`; the verifier
  driver is not Maven/Surefire-bound.
- Standalone/legacy Analyzer and Reader-to-Analyzer fallbacks are not equivalent to Bundle formal
  mode. Missing remote Analyzer configuration can fall back inline, and the standalone Analyzer
  retains development credential defaults; production operators must override them explicitly.

## Runtime and security boundaries

- Full-reactor development requires JDK 25. Core, Analyzer, and the combinatorics library target
  Java 21 bytecode; Reader and Executor target Java 25.
- The default execution-policy profile is `trusted-local`. It is unsandboxed, inherits host
  privileges/network, and Java candidates run inside the Executor process. Use it only for trusted
  code.
- `generated-default` and `networked-api-probe` select container isolation and fail closed if their
  required backend is unavailable. That fail-closed guarantee applies after a secure profile is
  explicitly selected; it does not make the default safe for untrusted candidates.
- Dependency JARs, model/checkpoint files, pickle/joblib artifacts, workbooks containing executable
  source, and generated candidate code are trusted-input boundaries unless a secure profile and
  artifact provenance policy say otherwise.
- No root project licence has been selected. The broad historical legal-option kit is deliberately
  omitted from this QA edition; its non-operative personal-use direction is recorded under
  [`docs/qa_edition/`](qa_edition/README.md).

The configured root defaults to repository-local `suts/`; use `BUNDLE_SUT_ROOT` for the companion
checkout. `advanced_surrogate2`, `shape_vs_sieve`, `FW_scenario_inputs`, the tutor, pub fixture,
pricing/security tryouts, and other experiments are not canonical resolver entries. Some use cases
address them directly; do not infer resolver support merely because a directory exists.

Important SUT truth:

- Pricing, secure-pipeline, tutor, and pub examples deliberately contain oracle-visible defects.
  They are fault-seeded test targets, not production implementations.
- Fintech runtime state is in memory. Its SQL file is a reference seam and currently differs from
  runtime states. Security/admin secrets and nonce stores are development-grade.
- Surrogate services mutate local memory/training/model files and expose unauthenticated local
  endpoints. Pickle/joblib and PyTorch checkpoint loads require trusted artifacts.
- GPT-2/GPT-4-Lite directories contain fragments that rely on shared definitions; they are not
  independently importable packages.
- Shape-vs-sieve is an experimental GUI/rendering lineage with approximate projection and verdict
  semantics; it is not a canonical Bundle integration.
- The 3D SUT uses heuristic search and quality-dependent polygon/slab geometry. Its API is local,
  unauthenticated, and has known concurrency, stale-result, resource-bound, path-containment, and
  browser DOM-safety limitations documented in its README.
